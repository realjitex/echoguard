# EchoGuard — заявки и защита Minecraft-аккаунтов через Discord

Связка Discord-бота и плагина для Paper: принятие заявок добавляет игроков в whitelist, первый вход требует привязки Discord, а последующие входы — подтверждения в личных сообщениях.

**Версия плагина: 1.0.2 · Minecraft / Paper: 1.21.11 · Java: 21**

## Возможности

- Добавление в Minecraft whitelist кнопкой **«Принять»** в Discord-тикете.
- Одноразовая привязка Minecraft-аккаунта к Discord через временный код.
- Подтверждение каждого нового входа кнопками **«Подтвердить вход» / «Отклонить»**.
- Одноразовое разрешение на подключение с подтверждённого IP.
- Допуск сотрудников без подачи заявки командой `/echoallow ник`.
- Сохранение привязок, очереди добавления и данных заявок в SQLite.
- Подписанные запросы и ответы между плагином и ботом.

Проверка Discord обязательна и для лицензионных игроков, и для игроков с offline-аккаунтами. OP не освобождает от неё. Отказ в подтверждении входа не банит игрока.

## Как устроена связка

Бот принимает заявки и хранит привязки. Плагин на игровом сервере обращается к HTTP API бота, выполняет добавление в whitelist и проверяет разрешение на вход.

Плагин устанавливается на **Paper-сервер**, а не на Velocity. Текущая версия рассчитана на один защищаемый игровой сервер. Discord TOKEN нужен только боту; плагин использует отдельный ключ `BRIDGE_SECRET`.

## Требования

- Paper 1.21.11 и Java 21.
- Python 3.10–3.12; локальные проверки выполнены на Python 3.12.
- Discord-бот с доступом к серверу, тикетам и каналу архивирования.
- TCP-порт хостинга бота, доступный с Minecraft-сервера.
- Возможность сохранять файлы бота и SQLite между перезапусками.

## Установка Discord-бота

1. Поместите `app.py` и `requirements.txt` в папку бота. Существующие изображения панелей, включая `Logo.png`, оставьте на прежних местах.
2. Установите зависимости:

   ```bash
   python -m pip install -r requirements.txt
   ```

3. В Discord Developer Portal включите для бота **Server Members Intent** и **Message Content Intent**. При приглашении нужны scopes `bot` и `applications.commands`.
4. Выдайте боту права на просмотр каналов, чтение истории, отправку сообщений, embed и файлов, управление каналами, ролями и никами. Роль бота должна находиться выше выдаваемых им ролей.
5. В `app.py` настройте Discord TOKEN, ID категорий, каналов, ролей и администраторов под свой Discord-сервер. Этот бот содержит панели конкретного проекта: при переносе нельзя оставлять чужие ID.
6. Настройте параметры связи в том же `app.py`:

   ```python
   BRIDGE_HOST = "0.0.0.0"
   BRIDGE_PORT = 5001
   BRIDGE_SECRET = "ВАШ_СЛУЧАЙНЫЙ_КЛЮЧ_ИЗ_64_HEX_СИМВОЛОВ"
   ```

   Для новой установки ключ можно сгенерировать командой:

   ```bash
   python -c "import secrets; print(secrets.token_hex(32))"
   ```

   При обновлении сохраните действующий ключ. Токен и ключ остаются в `app.py`; `.env` не требуется.

7. Запустите бота:

   ```bash
   python app.py
   ```

В Pterodactyl используйте выделенный хостингом TCP-порт: значение в `BRIDGE_PORT` само по себе не открывает порт снаружи. Запускайте только один экземпляр бота с этой базой данных.

## Установка плагина

1. Поместите `EchoGuard-1.0.2.jar` в `plugins/` защищаемого Paper-сервера. Удалите старый JAR EchoGuard, если обновляетесь.
2. Запустите сервер один раз для создания `plugins/EchoGuard/config.yml`, затем остановите его. До настройки связи EchoGuard отклоняет подключения.
3. Заполните конфигурацию:

   ```yaml
   bot-url: 'http://BOT_HOST:5001'
   bridge-secret: 'ТОЧНОЕ_ЗНАЧЕНИЕ_BRIDGE_SECRET_ИЗ_APP_PY'
   request-timeout-seconds: 8
   ```

   `BOT_HOST` — адрес хостинга бота. Префикс `http://` или `https://` обязателен. Не копируйте сюда Discord TOKEN.

   `127.0.0.1` подходит только при доступности бота через localhost именно из процесса Minecraft. У отдельных контейнеров localhost обычно разный.

4. В `server.properties` включите:

   ```properties
   white-list=true
   ```

5. Полностью перезапустите сервер. Не используйте `/reload` или горячую перезагрузку плагина.
6. Проверьте `/echoguard` в Minecraft и `/mc_status` в Discord. Сразу после запуска подождите несколько секунд для первого обмена.

Для публичного соединения рекомендуется HTTPS через reverse proxy. Путь `/bridge/*` должен передаваться боту без изменения. HMAC защищает от подмены запросов, но обычный HTTP не шифрует их содержимое. Часы хостов должны быть синхронизированы: допустимое расхождение — 30 секунд.

## Порядок работы с заявками

1. Администратор публикует панель командой `/create_panel channel:КАНАЛ`. При обновлении уже существующую панель пересоздавать не нужно.
2. Игрок заполняет заявку с Minecraft-ником.
3. Сотрудник нажимает **«Принять»** в тикете.
4. Бот ставит добавление в очередь, а плагин добавляет игрока в обычный whitelist.
5. После подтверждения Minecraft бот выдаёт роль, уведомляет игрока, архивирует тикет и закрывает его.
6. Игрок подключается к Minecraft и выполняет привязку по инструкции ниже.

Если Minecraft недоступен, задание остаётся в очереди, а тикет — открытым. После восстановления связи нажмите «Принять» повторно для завершения обработки. Ошибка выдачи роли или архивирования также оставляет тикет открытым.

Автор заявки должен оставаться участником Discord-сервера. Если он вышел, сначала пригласите его обратно с того же аккаунта.

## Инструкция для игрока

### Первый вход: привязка

1. Дождитесь принятия заявки или допуска администрацией.
2. Подключитесь к игровому серверу. Вас отключит с экраном привязки и кодом.
3. Отправьте **только код** боту в личные сообщения. Для принятой заявки используйте Discord её автора.
4. После успешной привязки подключитесь ещё раз, чтобы получить запрос подтверждения входа.

Код состоит из 10 символов и действует 10 минут. Каждая обработанная ботом новая попытка подключения до привязки выдаёт новый код и отменяет предыдущий. Если переподключались, отправляйте последний показанный код.

Коды генерируются через `secrets`, а база проверяет их уникальность. При совпадении генерируется другой код. С версии 1.0.2 учтённые базой коды не выдаются повторно, пока база сохранена. Одновременные попытки разных игроков не перезаписывают коды друг друга.

### Каждый следующий вход

1. Попробуйте подключиться к серверу.
2. Откройте сообщение бота в Discord: проверьте ник и IP.
3. Если подключаетесь вы, нажмите **«Подтвердить вход»**.
4. Подключитесь повторно с того же IP в течение **90 секунд**.

Разрешение расходуется на одну попытку входа. После выхода потребуется новое подтверждение, даже если IP не изменился. Если подключение отклонит другой плагин после проверки EchoGuard, подтверждение тоже может потребоваться заново.

Если это чужая попытка, нажмите **«Отклонить»**. Бана не будет; новый запрос можно получить через 15 секунд. Сам запрос подтверждения действует 3 минуты. Повторные подключения во время ожидания не создают множество одинаковых сообщений.

Если IP изменился после подтверждения, дождитесь истечения разрешения и начните заново. Вход с другим IP не расходует разрешение для подтверждённого адреса.

## Допуск сотрудников без заявки

На сервере, где установлен EchoGuard:

```text
/echoallow mygui
```

В консоли:

```text
echoallow mygui
```

Команда доступна OP или обладателю права `echoguard.admin`. Она добавляет ник в обычный Minecraft whitelist. После этого сотрудник самостоятельно получает код, отправляет его боту и подтверждает каждый вход как обычный игрок.

Команда не сбрасывает существующую привязку, не снимает баны и не отключает Discord-проверку. Если ник уже закреплён за незавершённой заявкой, завершите её принятие.

Уже находящиеся в обычном whitelist игроки также могут пройти самостоятельную первичную привязку без новой заявки.

> На offline-сервере ник сам по себе не доказывает владение аккаунтом. Для игрока, добавленного только через `/echoallow` или обычный whitelist, первый человек, получивший код под этим ником, может привязать свой Discord. Для предварительного закрепления за конкретным участником используйте `/mc_assign`; для принятых заявок Discord владельца уже известен боту.

## Команды

### Minecraft

| Команда | Назначение | Доступ |
| --- | --- | --- |
| `/echoallow <ник>` | Добавить игрока в whitelist с обязательной привязкой и подтверждениями | OP / `echoguard.admin` |
| `/echoguard` | Показать состояние связи с ботом | OP / `echoguard.admin` |
| `/minecraft:whitelist list` | Посмотреть обычный whitelist | Стандартные права сервера |
| `/minecraft:whitelist remove <ник>` | Удалить из обычного whitelist | Стандартные права сервера |
| `/minecraft:whitelist reload` | Перечитать whitelist после изменения файла | Стандартные права сервера |

В консоли команды вводятся без начального `/`. Префикс `minecraft:` позволяет вызвать стандартную команду, когда `/whitelist` перехватывает другой плагин.

### Discord

| Команда | Назначение |
| --- | --- |
| `/mc_status` | Проверить связь с Minecraft |
| `/mc_assign member:УЧАСТНИК nickname:НИК` | Закрепить ник за конкретным Discord и добавить в whitelist; привязка кодом и подтверждения остаются обязательными |
| `/mc_ticket_owner member:УЧАСТНИК nickname:НИК` | Восстановить владельца старой заявки; выполнять внутри её тикета, затем нажать «Принять» |
| `/create_panel channel:КАНАЛ` | Опубликовать панель заявок |
| `/create_panel2 channel:КАНАЛ` | Опубликовать панель поддержки |
| `/create_panel3 channel:КАНАЛ` | Опубликовать панель уведомлений |
| `/create_panel4 channel:КАНАЛ` | Опубликовать панель команды |
| `/create_panel5 channel:КАНАЛ` | Опубликовать панель суда и идей |
| `/help_panel` | Показать справку по панелям |

Команды `/mc_*` требуют прав администратора Discord. `/mc_assign` не предназначена для обхода конфликта существующих привязок. Самостоятельной команды сброса привязки для игроков нет.

## Velocity и смешанные аккаунты

EchoGuard не меняет режим авторизации прокси и не проверяет сессию Mojang. Вопрос допуска offline-клиентов решается настройками Velocity и его плагинов авторизации.

При использовании Velocity:

- Установите EchoGuard на защищаемый Paper backend.
- Настройте согласованную передачу UUID и реального IP между Velocity и Paper.
- Закройте возможность прямого подключения к backend в обход прокси.
- Сохраняйте стабильную схему UUID: переход между premium/offline-профилями может вызвать несовпадение whitelist или существующей привязки.

EchoGuard не отменяет отказ другого плагина. Самостоятельная первичная привязка через whitelist не заменяет проверку владения ником в offline-режиме.

## Частые проблемы

| Сообщение / симптом | Что проверить |
| --- | --- |
| «Защита настраивается» | В `bot-url` есть схема `http://` или `https://`, ключ состоит из 64 hex-символов, после настройки выполнен полный перезапуск |
| «Связь с Discord временно недоступна» | Бот запущен, внешний TCP-порт доступен с Minecraft, адрес и ключ совпадают, часы синхронизированы |
| «Сначала дождитесь принятия заявки» | Заявка завершена либо игрок допущен через `/echoallow`; для незавершённой заявки завершите принятие |
| Не удаётся определить автора тикета | Автор не вышел из Discord; при неоднозначной старой заявке используйте `/mc_ticket_owner` внутри неё |
| Игрок есть в whitelist, но не входит | Сравните UUID подключения и записи whitelist; проверьте отдельные whitelist других плагинов, включая FlectonePulse |
| `/whitelist` отвечает чужой справкой | Используйте `/minecraft:whitelist ...` для встроенного списка |
| Код не принимается | Отправьте только последний код в ЛС; проверьте срок и Discord автора заявки |
| Бот не может написать в ЛС | Разрешите личные сообщения от участников общего Discord-сервера и разблокируйте бота |
| После галочки снова не пускает | Подключитесь с подтверждённого IP в течение 90 секунд; проверьте другие плагины и штатный whitelist |
| «Идентификатор аккаунта изменился» | Проверьте настройки UUID на прокси; смена профиля требует проверки администратором |
| «Недействительная сессия» | Проверьте режим авторизации Velocity и premium-проверки его auth-плагинов; это не сообщение EchoGuard |

Недоступность бота не отключает защиту: новые подключения отклоняются до восстановления связи.

## Обновление и резервные копии

1. Остановите бота и Minecraft.
2. Сделайте резервную копию папки бота, `whitelist.json` и конфигурации EchoGuard.
3. Замените `app.py` и старый JAR актуальными версиями; не оставляйте два JAR EchoGuard.
4. Сохраните свои TOKEN, `BRIDGE_SECRET`, порт, ID Discord, изображения и `plugins/EchoGuard/config.yml`.
5. Обязательно сохраните `echo_guard.sqlite3`. Не подменяйте её пустой базой.
6. Запустите оба процесса и проверьте команды статуса.

База содержит привязки, заявки, очередь команд, запросы входа и учёт выданных кодов. При работающем боте рядом могут находиться файлы `-wal` и `-shm`; для простой файловой резервной копии сначала полностью остановите бота.

Обновление не требует удаления открытых тикетов или пересоздания панелей. Если данных старого тикета недостаточно для определения автора, предусмотрена команда восстановления.

Архив тикета сохраняет текст, embed и ссылки на вложения. Сами вложения не скачиваются; ссылки Discord не являются постоянной резервной копией файлов.

Для отзыва доступа удалите игрока из стандартного whitelist и снимите OP, если он был выдан. Для уже подключённого игрока отдельно завершите его текущую сессию. Это не удаляет привязку Discord.

## Сборка и проверки

Сборка плагина с JDK 21 и Maven:

```bash
cd plugin
mvn package
```

Результат: `plugin/target/EchoGuard-1.0.2.jar` относительно корня проекта.

Тесты бота из корня проекта:

```bash
python -m pip install -r requirements.txt
python -m pip install pytest pytest-asyncio
python -m pytest tests -q
```

Для версии 1.0.2 пройдены 29 локальных тестов, включая обновление кодов, искусственные коллизии, параллельные запросы, привязку, одноразовые разрешения и сохранение тикетов при ошибках. JAR собран против Paper API 1.21.11. Проверки на живом Minecraft/Discord этим набором тестов не заменяются: после установки проверьте полный цикл на тестовом игроке.

## Публикация на GitHub

Этот README не содержит действующих секретов. **Рабочий `app.py` и ранее полученный полный архив содержат настройки и секреты вашей установки — не публикуйте их как есть.**

Перед публикацией кода подготовьте отдельную копию `app.py`: замените Discord TOKEN и `BRIDGE_SECRET` заглушками, а внутренние ID — примерами. В рабочем файле настройки могут по-прежнему храниться прямо в Python; переход на `.env` не требуется.

Не добавляйте в репозиторий:

- SQLite-базу, файлы WAL/SHM и их резервные копии;
- рабочий `plugins/EchoGuard/config.yml` с ключом;
- логи и архивы тикетов с данными игроков;
- ZIP-архивы, содержащие перечисленные файлы.

Если секрет уже попал в публичный репозиторий, замените его: удаления строки из последнего коммита недостаточно, поскольку она остаётся в истории Git.
